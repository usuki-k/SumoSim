# ARCHITECTURE

現在確定しているArchitectureのみを記す。未導入TechnologyをCurrentとして書かない。

## 確定

- Vite + TypeScript + Phaser 4
- Web-native
- Backendなしで開始
- Pure TypeScript simulation と Phaser presentation の分離
- Phaser Sceneをgameplay source of truthにしない
- deterministic / testableなgame logicはできるだけPure TypeScriptへ置く
- frame rate依存のgameplay calculationを避ける（fixed timestep + accumulatorを採用。下記「現状」参照）
- 長期management stateとbout runtime stateは分離する方向
- Platform integrationはadapter境界を作る方向。CrazyGames SDKをgameplay coreへ直接散らさない

## ゲームルールと描画の分離

```
Pure TypeScript Game / Simulation
        ↓
State / Results
        ↓
Phaser Rendering / Input / Animation
```

例（命名は決定事項ではない）：

- `BoutSimulation`: 相撲ルール、移動結果、stamina、balance、押し計算、ring-out / 勝敗条件、必要に応じてCPU判断の入力
- `BoutScene`: input、rendering、sprite、animation、camera、sound、presentation

Sceneのframe/updateに重要なGameplay Formulaを埋め込まない。
同じ意味のStateのSource of Truthを複数持たない。

## 初期Prototypeの方針

Small explicit designを優先し、過剰なFramework、ECS、DI Framework、Global Event Bus、汎用Rule Engine等を先回りで導入しない。

## 現状

- `src/main.ts`がPhaser Gameを起動する。logical sizeはProduct表示の基準である1920×1080（runtime artの座標空間と1:1。表示サイズは`Phaser.Scale.FIT`）。
- `src/game/sumo/`にPure TypeScriptのBout境界がある（Phaser import無し）：
  - `BoutSetup`: 明示的な入力境界（participant identity、初期logical position、ring半径）。将来のManagement Stateはこの形へ変換して渡し、Bout runtimeの正本にはしない。
  - `BoutSimulation`: Bout runtime stateの正本。Setupをcopyして保持し、不正Setup（participant数・id重複/空・非有限値・ring半径）を拒否する。
  - `BoutSnapshot`: `getSnapshot()`が毎回返すcopy。consumerが変更してもcanonical stateへ影響しない。
  - `BoutSimulation.step(intents)`: 1 logical tick（60Hz、暫定）だけ進める。render deltaは受け取らない。participantごとのposition / velocity / facingがcanonical state。
  - `ParticipantIntent { move, pushPressed, tsuppariLeftPressed, tsuppariRightPressed, counterPressed, gripPressed, driveHeld }`: source非依存のsemantic入力。`move`はworld-frame vector（Simulation側で長さ1にclamp）、`pushPressed` / `tsuppariLeftPressed` / `tsuppariRightPressed` / `counterPressed` / `gripPressed`はそのtickの新しい押下edge（holdではない）。同じtickの優先順は Push > Tsuppari（使える左 > 使える右。cooldown中の手のedgeは先に捨てる）> Counter > Grip で、負けたedgeは捨てる（queueしない）。`driveHeld`は押しっぱなしの状態（edgeではない）で、GRAPPLED中にREADYのときだけ使う（FREE中は無視）。raw keyはSimulationに入らない。
  - Movement model（grounded、self velocityに適用）: velocityをintent方向の平行成分と垂直成分に分解する。垂直成分は強く減衰（方向転換で滑らない）、逆向きの平行成分はまず制動で0へ、同方向は段階的に加速、入力なしは0まで制動、全体はMAX_SPEEDでclamp。velocityは引き続きcanonical state。係数は暫定（User Play Test対象）。→ position積分。facingは毎tick末に相手方向へ即時（座標系: +x右、+y下、facing 0 = +x、radian）。同一点では直前のfacingを維持。
  - `FixedStepAccumulator`: frame deltaを整数tick数へ変換（Phaser非依存）。1 frameのdelta上限とtick数上限を持ち、超過分は破棄。
- `src/game/input/movementVector.ts`: キー状態 → world-frame vector（画面基準: W=-y, S=+y, A=-x, D=+x。逆方向は相殺、斜めは正規化）。
- `src/game/input/pressLatch.ts`: key-downで1つの押下edgeを保持し、次のsimulation tickが1回だけ消費する（tick 0のframeでも失われず、1 frame内の複数tickへ重複しない）。SceneはArrowUp（Push）、ArrowLeft / ArrowRight（左手 / 右手のTsuppari）、ArrowDown（Counter）、Shift（Grip / Release。左右どちらでも同じ）（いずれも暫定binding）のPhaser key `down`（auto-repeatなし）を、それぞれ別instanceへ接続する。
- `src/game/input/pushDummyController.ts`: Contested Push検証用のPrototype harness（CPU AIではない）。Snapshot幾何だけを読み、毎Simulation tickに通常の`ParticipantIntent`を返す。mode `stationary`（零入力）/ `push`（離れていれば相手へmove、Contactなら移動せず、idleかつcooldown（`DUMMY_PUSH_COOLDOWN_TICKS`=30 tick、action終了後またはKuzushi終了後のidle stable tickから数える）明けに`pushPressed`を1回。Kuzushi中は零入力、GRAPPLED中は`driveHeld = true`だけを出す（STATIONARYでは出さない）。いずれもcooldownを満タンに保持し、次のidle / stable / FREE tickから数える。Gripもreleaseも出さない）。mode `tsuppari`（ACTION-07B）は、中心距離が`DUMMY_TSUPPARI_RANGE`（0.8 m。Simulationのreachより内側のharness値）を超えていれば相手へmoveし、範囲内では、相手が`DUMMY_TSUPPARI_RECEDE_SPEED`（0.1 m/s）より速く離れている間は待ち、idle / stableでSnapshotの`tsuppariCooldown`が0の手（左を優先、だめなら右）のedgeを1回出す（harness独自のcooldownは無い。命中 / reachの判定はSimulationだけ）。Simulation stateへ直接触れず、Push phaseも迂回しない。SceneはキーをMode切替（`1`=STATIONARY / `2`=PUSH / `3`=TSUPPARI、既定STATIONARY）に接続し、`R`はModeを保持してcontroller timingをresetする。
- `BoutScene`: Phaser keyboardを読んでIntentを作り、accumulatorで0..N tick進め、Snapshotを永続GameObjectへ一方向同期する。canonical stateは持たない。participant identityとcontroller / 見た目の対応（`PARTICIPANT_PRESENTATION`）はSimulation外のScene側にある。Opponentの駆動は`PushDummyController`（上記）。
- 暫定の力士visual（VISUAL-01A）: `src/game/presentation/wrestlerVisualState.ts`（Phaser非依存のpure mapping）の`resolveWrestlerVisualState(self, opponent, engagement, outcome, wasMoving)`が、Snapshotから見た目の状態（pose: idle / move / push / tsuppari / counter / kuzushi / grip / grapple / drive、push / grip / tsuppariのphaseと進み具合、tsuppariの手、grappleの役割 neutral / morozashi-holder / morozashi-disadvantaged、turning、frozen、自分の足運びの速さ、Kuzushiの残り）を導く。優先順位は kuzushi > FREEのpush / tsuppari / counter / grip > drive > grapple（turning / 役割）> move（hysteresis付き）> idle で、勝敗の確定はfreezeの修飾として扱う。readinessは既存の`canActInGrapple`を読むだけで、gameplayの式は複製しない。`src/game/scenes/WrestlerView.ts`は、Product力士（下記ACTION-ART-03A）を剛体の1枚のspriteとして描く。visual stateは移動のhysteresis（`moving`）にだけ使い、部位の変形やposeの補間はしない。`src/game/scenes/DohyoView.ts`は、Product背景（下記ACTION-ART-01B）を表示する。debug表示はkey `0`で切り替える（既定はOFF）。ONにすると、従来のlabel / phase text / engagement readout / 接触円の輪郭 / facing marker / 組みの線と、Tsuppariのreadout（phase textの`TSU L` / `TSU R`と`HIT` / `WHIFF`、左下のdebug行に、各参加者の左右の手のcooldown（秒）とbuildup `hits n/5`）を表示する。Tsuppari中は、その手のProduct Tsuppari pose（下記ACTION-07D）を行動全体のあいだ表示する。visualはgameplayのstateを持たず、変更もしない。
- 単位: simulationはmeter、m/s、radian。meter→pixelのscale + translateはScene側（presentation）。
- Vitest導入済み（`pnpm test`）。
- 速度・加速度・減速度・tick rate・ring半径・spawn位置・body半径・色・logical sizeはPrototype / 暫定値でありFinal値ではない（User Play Testで調整する）。
- Contact（ACTION-03A）: 各participantはSimulation所有の円（`bodyRadius`、Snapshotで公開。暫定で同値0.35m）を持つ。`step()`の順序は 移動入力のsanitize → grounded self velocity更新 → position積分 → contact解決 → facing更新。contact解決は、`CONTACT_SLOP`付きの距離判定、法線A→B（同一点ならAのfacing方向）、接近方向の法線速度成分のみ除去（接線成分は保持、反発なし）、重なりの位置補正（接近方向のself velocity成分＝inward contributionの比で配分し、静止している側は動かさない。寄与が無い場合は動いている側のみ、両方または両方動いていなければ50/50。質量重み付けなし）。非接触時の移動はACTION-02Bと同一。
- Push（ACTION-03B。timingとforceの時間はACTION-10Bで下記のPush chargeに変わった）: 1押下 = 1回の離散Action（`action`: idle | push{startup / active / recovery, ticksRemaining, direction, impactTicksRemaining}）。開始時のfacingで方向を固定し、Action中はWASD操作を無効化（startup / recoveryは入力0として制動、activeは固定方向へgrounded ruleで踏み込む）。Action中の押下は無視（queueしない）。velocityは`selfVelocity`（自分の足運び。grounded ruleとcontactのclosing除去はここだけ）と`externalVelocity`（相手のPushで受けた運動量。独自の減衰とMAX clamp）に分離し、移動は和で行う。Snapshotの`velocity`は和（実際の移動速度）、`externalVelocity`はその内訳。contact中の、impact windowが開いているPushは net（A:+1, B:−1）× `PUSH_EXTERNAL_ACCELERATION`を法線方向に両者のexternalへ同量加える（同時Pushは相殺）。`step()`の順序: intent → Push開始 → 実効move → self velocity → external減衰 → 積分 → contact → Push解決 → Push timer → facing。数値はすべて暫定。
- Push charge（ACTION-10B。ACTION-10AのOption B、User選択。暫定、User Play Test対象）: Pushは「長く、まっすぐ、途中で変えない突進」になった。`action`のpushに`impactTicksRemaining: number | null`を追加（Snapshotにもcopy）。startup `PUSH_STARTUP_TICKS`=6（入力0で制動、力なし）→ active = 押下時のfacingから固定した`direction`への突進（最大`PUSH_CHARGE_TICKS`=24 tick、既存のgrounded rule・`MAX_SPEED`のまま。WASDは無視、相手を追わない）→ recovery `PUSH_RECOVERY_TICKS`=10。activeで最初に体が接触したtick（`resolveContact`の直後、Counter / 力の解決より前）に、impact window `PUSH_IMPACT_TICKS`=8（旧`PUSH_ACTIVE_TICKS`の力の長さ。値は1つ）が開く。Push力（接触しているtickだけ）、Counterで捕えられる時間、Push vs Tsuppariの連結は、このwindowのあいだだけ。windowは接触が切れても毎tick数え続け、再接触で開き直さない。0になるとそのままrecoveryへ（残りの突進は再開しない）。activeの`ticksRemaining`は残りの突進で、window中は数えない。接触しなければ24 tickを走り切ってrecoveryへ（相手が逃げても止まらない）。自由空間の移動は約0.938 m（旧0.127 mの7.4倍、peak 3.0 m/s）。接触から始めたPushは従来と同じ（force 8 tick、shove 0.5325 m）。Push中（startup〜recovery）はcanonical facingを凍結する（Kuzushiと同じく`updateFacing`で飛ばす。体は突進の方向を向いたまま。idleに戻ると相手の方向へ向き直る）。横の回避は通常のMoveと既存の円の接触だけで決まり、早い読みは空振り、遅い反応は当たる。空振りで縁を越えれば、既存の`resolveArenaRingOut`で攻撃側の負けになる（自滅専用の規則、壁、縁での制動は無い）。同時のPushは、両者のwindowがactiveのあいだnet 0で打ち消し合う。
- Counter + Kuzushi（ACTION-04A1）: `action`に`counter{ticksRemaining}`（window 1 phase、`COUNTER_WINDOW_TICKS`=12）を追加。開始はidleかつstableのときだけで、Contact不要。window中はWASD無効（入力0として制動）。window中に「相手Pushのimpact windowが開いている × そのtickの実Contact」が成立した最初のtickで成功し（ACTION-10B: 接触前の長い突進は捕えられない）、相手のPushをcancelしてKuzushiへ入れ、Counter使用者は即idleへ戻る（contact解決の後、Push力解決の前に判定するので、そのtickのPush力は掛からない）。tierは`counterTier()`で、相手のimpact windowの経過tick（ACTION-10B: 突進の開始ではなく最初の接触から数える。長い突進の後の最初の接触もBestになり得る）が`COUNTER_BEST_TICKS`（=3、経過0〜2）未満ならBest、それ以外はSuccess。windowが切れたらFailで、使用者自身がKuzushi。Kuzushiは`action`とは別の`posture`（stable | kuzushi{ticksRemaining}）で、入口は`enterKuzushi()`だけ（actionをidleにする。不変条件: kuzushi ⇒ action idle）。`KUZUSHI_TICKS`=90（1.5秒。ACTION-09Bで30から変更）の完全tickのあいだ最大で持続する（tick先頭でtimerを進め、0なら入力処理の前にstableへ戻る。入ったtickは数えない）。Kuzushi中はPush / Counterを開始できず（queueしない）、移動入力0で制動、facingは固定（`updateFacing`をskip）。押し込まれる側がKuzushiなら、Push加速度に`KUZUSHI_FOLLOWUP_FORCE_MULTIPLIER`（=1.5。旧名`KUZUSHI_PUSH_SUSCEPTIBILITY`）を掛ける（下記のfollow-up）。将来のGrip保証は「有効range判定を通過した後、Kuzushiなら成功」とする境界だけを決めてあり、未実装。`step()`の順序: posture timer → intent → Push / Counter開始 → 実効move → self velocity → external減衰 → 積分 → contact → Counter解決 → Push解決 → action timer（Counter期限切れ → Kuzushi）→ facing（Kuzushiはskip）。Sceneは`KUZUSHI`（優先）/ `COUNTER`を表示する。数値はすべて暫定。
- Counter位置解決（ACTION-04A2 → ACTION-04A4）: 成功時、`resolveCounter`はPushをcancelする前に攻撃側（pusher）のlocked Push方向`d`を控え、`counterRelocationTarget()`（pure）で防御側（Counter user）の目標を決める。基準の`P`は、ACTION-04A4から、pusherの捕えた位置を`d`へ`COUNTER_STAGGER_DISTANCE`（= 1.0R = 0.35 m）進めた終点。候補は、Counter transition（下記）で到達する。基準は攻撃側の中心`P`、`perp = (-d.y, d.x)`、`R` = 半径の和。候補はrear `P - dR`、side+ `P + perp R`、side− `P − perp R`（いずれも重なりのないContact距離ちょうど）。sideの優先: 防御側のlateral offset `dot(perp, defender − P)`の符号（±`COUNTER_SIDE_EPSILON`=1e-6 m以内はtie）。tieなら土俵中心に近い方、それも同じならside+。Bestは rear → 優先side → 反対side、Successは 優先side → 反対side の順に試し、最初のvalidな候補を採る（valid = 有限かつ`|target| <= arena.radius − bodyRadius`。clampはしない）。全候補がinvalidなら、Counter transitionは始まらず、ACTION-04A2のfallbackのまま（移動しない、tierとKuzushiはそのまま、攻撃側にだけ`d × COUNTER_OVERSHOOT_SPEED`（=1.0 m/s）をexternalVelocityへ加え、既存のMAX clampと減衰に任せる、pair external momentumは消さない）。Failは従来どおり（移動・overshoot・transitionなし）。
- Counter transition（ACTION-04A4）: 有効な候補があるCounter成功は、Simulationが持つpair-levelの`counterTransition`（`none` | `active{tier, counterUserId, pusherId, ticksRemaining}`。Snapshotのtopレベルにcopyを公開。pathの内部値は公開しない）を始める。
  - 捕えたtick: 位置は動かさない（瞬間移動しない）。2人のself / external velocityを0にする（既存の勢いは遷移に吸収する）。pusherはKuzushi、Counter userはidle / stable。このtickの残り（Grip / Push / timer / facing / ring-out）は通常どおり。
  - 続く`COUNTER_TRANSITION_TICKS`（=90、約1.5秒。ACTION-04A5で120から短縮）tickは、`step`が`stepCounterTransition`だけを行う。intentは読まない（2人とも入力lock。押下edgeは捨てられ、溜まらない）。pusherのKuzushi timerは止める。接触 / Push / Counter / Grip / 組み / Driveの処理、通常の積分は行わない。
  - 位置はpathだけが決める。u = k / 90。pusherは`P0 + d · L · (1 − (1 − u)²)`。Counter userはpusherを中心に、`(d, perp)`系の極座標で、捕えた時の(半径, 角度)から(半径の和, 目標の角度)へsmoothstepで移る（side± = ±π/2、rear = 優先sideの符号 × π。pusherの体を通り抜けない）。最後のtickでは、pusherの終点と目標の候補へ厳密に置く（Success = 終点の真横、Best = 真後ろ、半径の和ちょうど）。
  - 速度は、そのtickのpathの変位を報告する（pusherはexternal、Counter userはself。積分には使わない）。facingは既存の規則（pusherはKuzushiで固定、Counter userはpusherへ向く）。
  - ring-outは毎tick、2人とも既存の`resolveArenaRingOut`（直前 → 現在の線分、Tokudawara対応、境界ちょうどはIN、先に出た方の負け、同時はRematch）。Counter userにも免除はない。途中で決着すると、既存のfreezeでその状態のまま止まる（完了はしない）。
  - 完了（90 tick目の終わり、ongoingのとき）: 2人の速度を0にし、pusherのKuzushiを`KUZUSHI_TICKS`から改めて始め（Counter → Grip → Morozashiの機会を保つ）、`counterTransition`を`none`にする。次のtickから入力が戻る。
  - dummy harnessは、`counterTransition`が`active`の間は入力せず、Push cooldownを満杯に保つ。
- Grip / Engagement（ACTION-05A）: pair-levelの`engagement`（`free` | `grappled{advantage: neutral | morozashi{holderId}}`）をSimulationが1つだけ持つ（participantに組みのflagは持たせない）。初期値は`free`で、Snapshotのtopレベル`engagement`として独立したcopyを公開する。`action`に`grip{reach | recovery, ticksRemaining, direction}`を追加（`GRIP_RECOVERY_TICKS`=12。reachの長さ、移動、成功の条件はACTION-11Cで下記の「Grip lunge + contest」に変わった）。Gripを開始できるのはFREEかつidleかつstableのときだけ。成立した時点で相手がKuzushiなら`morozashi(holder = 掴んだ側)`とし、相手のKuzushiは即座に消費してstableにする。それ以外はneutral。reachが切れたらwhiffでrecoveryへ入る（Kuzushiにはならない）。成立は`enterGrapple()`だけで行い、両者のactionをidleにし、両者の`externalVelocity`を成分ごとの平均にそろえ（同じ体格を仮定した暫定の正規化）、中心距離を半径の和ちょうどへ対称に寄せる。GRAPPLED中は毎tick、通常のcontactの後に`resolveGrappleBond()`で半径方向の距離を対称に補正する。両者のWASDは無効（制動のみ）で、FREE用のPush / Counter / Gripの開始もない。facingの扱いは下記のGrappled Orientationを参照。GRAPPLED中のGrip edgeはrelease: そのtickの先頭でFREEに戻り、押した側だけがGrip recoveryに入る（同時なら両者）。release tickの他のFREE用edgeは捨てる。位置・速度・facingは変えず、Morozashiは消える。`step()`の順序は下記のKuzushi follow-upの項（ACTION-11C版）を参照。Sceneは上部に`ENGAGE: FREE / GRAPPLED / MOROZASHI (PLAYER|CPU)`を表示し、組み中は2人の中心を線で結ぶ（neutralは白い細線、Morozashiはholder色の太線）。phase textに`GRIP` / `GRIP REC`を追加した。数値はすべて暫定。

- Tsuppari（ACTION-07B、設計ACTION-07A）: 定数はすべて暫定（User Play Test対象）。
  - 入力: ArrowLeft / ArrowRight = 自分の左手 / 右手の押下edge。開始はFREE・release tickでない・idle・stableのときだけ（組み中、CounterTransition中、Kuzushi中、他のaction / recovery中のedgeは捨てる。queueしない）。優先順はIntentの項を参照。
  - `action`に`tsuppari{hand: left | right, phase: startup | active | recovery, ticksRemaining, strike: pending | hit | whiff}`を追加。startup 6 / active 1 / recovery 9 tick（合計16）。Tsuppari中はWASDを無効（入力0として制動。その場で打ち、自分では前へ出ない）。既存のexternal momentumはそのまま。方向は固定しない（命中tickの中心軸）。
  - 手ごとのcooldown（参加者の`tsuppariCooldown {left, right}`、Snapshotにcopyを公開）: 受け付けたtickでその手を`TSUPPARI_HAND_COOLDOWN_TICKS`（60）にする。勝敗が決まるまで、毎tickの先頭で1ずつ減る（CounterTransition中、Kuzushi中、組み中も）。同じ手はちょうど60 tick後に再び使える。左右は独立。
  - 命中: activeの1 tickだけで判定する。`中心距離 ≤ TSUPPARI_HAND_REACH（0.55 m。ACTION-07C2で0.525 mから変更、Provisional）+ 受け手のbodyRadius`（現在0.90 m。体の接触は不要。spriteの形は使わない）なら`hit`、そうでなければ`whiff`。
  - 力: 命中tickに、受け手のexternalVelocityへ攻撃側 → 受け手の向きに`TSUPPARI_IMPULSE`（2.13 m/s）を1回だけ加え、clampする。攻撃側には何も加えない。受け手がそのtickの前からKuzushiなら、`KUZUSHI_FOLLOWUP_FORCE_MULTIPLIER`（1.5）倍のimpulse（3.195 m/s、`MAX_EXTERNAL_SPEED`のclampは従来どおり）にし、そのKuzushiを消費する（下記のfollow-up）。代表fixture（接触、受け手idle）で受け手の変位は約0.266 m（旧Pushとほぼ同じ）。
  - 組の勝負: 接触していて、どちらかのPushのimpact windowが開いているtickは、Pushと同じく2人に同じ量を加える。量は`netPush · PUSH_EXTERNAL_ACCELERATION · s · dt + netStrike · TSUPPARI_IMPULSE · TSUPPARI_COUPLED_SHARE（0.5）`（netStrike = Aの命中 − Bの命中）。Tsuppariが無いtickの計算は従来どおり（同時Pushは打ち消し合う）。それ以外のtickでは、命中は受け手だけに入るので、同じtickのTsuppari同士は打ち消し合わず、両者が離れる。Pushのstartup中、接触前の突進中、impact windowの後に当たったTsuppariは、Pushの使用者への普通の命中。
  - buildup（参加者の`tsuppariBuildup`、Snapshotにcopyを公開）: 普通の命中で+1。`TSUPPARI_KUZUSHI_BUILDUP`（5）回のあとの6回目の命中は、普通のimpulseに加えて受け手をKuzushi（`KUZUSHI_TICKS`）にし、buildupを0に戻す。whiffとCounterで捕えられたTsuppariは、buildupを変えない。乱数なし。
  - 解決は`resolveForces`の1か所で、参加者の順序に依存しない: 両者の命中を同じ状態から決める → 力（組 / 受け手ごと。follow-upの1.5倍）→ follow-upで使われたKuzushiの消費 → 6回目の命中のKuzushi。
- Kuzushi follow-up window（ACTION-09B。暫定、User Play Test対象）: Kuzushiは最大1.5秒（`KUZUSHI_TICKS`=90）の、**最初に成功した1回のfollow-upで消費される**無防備な状態。入口（Counter Fail、Push Counterの捕獲、Tsuppariの捕獲、Tsuppariの6回目の命中）は変えていない。follow-upは次の3つだけ: (1) Kuzushiの受け手が実際に受けたPush力（active・接触・net ≠ 0。そのtickだけ`KUZUSHI_FOLLOWUP_FORCE_MULTIPLIER`=1.5倍、次のactive tickからは1.0倍）、(2) Kuzushiの受け手へのTsuppariの命中（1.5倍のimpulse）、(3) Kuzushiの相手への有効なGrip（数値の倍率ではなく、従来どおりMorozashiが利点。rangeは迂回しない）。Push / Tsuppariは`resolveForces`の先頭で、効果を加える前のKuzushi状態（`wasKuzushi`）を控えて倍率を決め、そのtickの力をすべて加えた後に`posture`をstableへ戻す（別の「消費済み」flagは持たない。kuzushi ⇒ action idleの不変条件はそのまま）。startup、recovery、接触の無いactive、打ち消し合うPush、whiff、range外 / 空振りのGrip、ただの接触、移動、減衰、待機は消費しない。Kuzushiを作る攻撃（6回目の命中）は、その新しいKuzushiの利点を受けない。受け手がすでにKuzushiなら、その命中は古いKuzushiで1.5倍になり、古いKuzushiを消費した後で、6回目の規則が新しい完全なKuzushi（90）を作る。Counter transitionのあいだは従来どおりpusherのKuzushi timerが止まり（入力lockで、follow-upも解決されない）、完了時に新しい90 tickのKuzushiが始まる。presentationの汗（`kuzushiStrength = ticksRemaining / KUZUSHI_TICKS`）は、そのまま長く表示され、消費されたtickで消える。倍率・消費・長さの判断はすべて`src/game/sumo/`にある。
  - Counter: Counter windowが、相手のTsuppariの命中tick（reach内）に開いていれば捕える。攻撃側はその場でKuzushi（位置も既存の勢いも変えない）、Counterの使用者はidleへ戻る。impulse、buildupの変化、移動、CounterTransition、overshoot、tierはどれも無い。Push Counterは従来どおり（接触が条件）。`resolveCounter`はFREEのtickで毎回呼び、Pushの分岐だけが接触を確かめる。
  - Ring-out: Tsuppariの勢いは既存の積分とring-out判定（同時ならRematch）にそのまま乗る。
  - `step()`の順序: Tsuppari cooldown → （CounterTransitionならその処理だけ）→ posture timer → release → FREE action開始 → 実効move → self velocity → external減衰 → 積分 → contact → bond（GRAPPLED）/ FREE: Push impactの開始 → Grip contest（1つの状態から決める、ACTION-11C）→ 負けたGripのrecovery → Counter → Gripのgrapple → Push + Tsuppariの力（まだFREEのとき）→ action timer → facing → ring-out。
- Push knockback（ACTION-07B）: `PUSH_EXTERNAL_ACCELERATION`を20 → 26.25 m/s²にした。代表fixtureで、Pushの受け手の変位は約0.267 → 0.533 m（約2倍）。timing、`MAX_EXTERNAL_SPEED`、`EXTERNAL_DECELERATION`、Kuzushiの倍率（当時の`KUZUSHI_PUSH_SUSCEPTIBILITY`、現在の`KUZUSHI_FOLLOWUP_FORCE_MULTIPLIER`）は変えていない（暫定、User Play Test対象）。
